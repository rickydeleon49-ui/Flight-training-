# Performance and usability polish — 13 September 2026

This branch starts at `origin/main` commit `15088e6` after the 12 September polish and Mac audit. It leaves the published `v0.5.1` tag, migrations, backup format, and bundle identifier unchanged. Measurements below are from a Windows development host. They are reproducible component or Rust benchmarks, not claims about launch-to-ready time or installed-app behavior.

## Bench setup and results

Host: Windows x64, AMD Ryzen 7 5800X3D (16 logical processors), 32 GiB RAM, Node 24.16.0, Rust 1.98.1. Benchmarks ran from a warm process; medians avoid one-off startup noise. No private data, Gemini credential, or uploaded handbook was used. Process peak memory and WebView paint time were not instrumented, so neither a memory reduction nor an end-to-end startup speedup is claimed.

| Scenario | Input and method | Before | After | Interpretation |
| --- | --- | ---: | ---: | --- |
| Study Library, small | 100 synthetic materials and matching actions; `renderToStaticMarkup`, five runs, median | 68.65 ms; 99,248 HTML chars | 65.64 ms; 99,325 HTML chars | No meaningful change expected when all cards fit. |
| Study Library, large | 2,500 synthetic materials/actions; same method | 221.16 ms; 2,312,648 chars | 9.55 ms; 99,447 chars | First page still covers the full filter/sort input, but mounts only 100 cards. |
| Study Library, very large | 5,000 synthetic materials/actions; same method | 436.64 ms; 4,620,148 chars | 7.81 ms; 99,447 chars | Roughly 56× less initial server-render time; not WebView paint, database loading, or subsequent “Show more” cost. |

The Study Library benchmark is `src/pages/StudyLibrary/StudyLibrary.bench.test.ts`; run it with `HFD_BENCH=1` and optionally `HFD_BENCH_OUT` to write JSON. The Quick Find benchmark is `src/logic/quickFind.bench.test.ts`. The PDF comparison is the ignored `pdf::tests::batch_deletion_benchmark`; run it explicitly with `cargo test batch_deletion_benchmark -- --ignored --nocapture`. Timings vary by host and warm-cache state. These test cases establish relative local evidence, not a guaranteed user-visible speedup.

## Changes and safety review

- Study Library computes next-action titles once per action set instead of scanning all actions for each card. Search, topic/type/status filters, and sort still consider every material. The grid shows 100 at a time, with a visible count and “Show 100 more materials” control. Changing a filter resets the page; a regression test covers paging, full-list search, and clearing a search. This bounds initial DOM work without imposing a database page size or hiding matching materials.
- Automatic and manual PDF extraction now removes unwanted page references in one pass and decrements page-tree counts in groups. This keeps the existing candidate-size search, 50 MiB/1,000-page ceilings, app-owned storage, original source, labels, database transaction, and cleanup paths. Tests compare output bytes with the old `lopdf::delete_pages` behavior for simple, nested-tree, and image-bearing PDFs. A real long image-heavy PDF, PDF viewer rendering, and memory pressure remain untested.
- Import, complete backup creation/inspection, and restore staging now execute as blocking worker tasks instead of Tauri's synchronous command handler on the UI thread. This should keep the window able to repaint during disk work; disk throughput itself was not measured. Import reports the bytes actually copied and deletes a partial destination after copy failure. Existing bounded SQLite snapshot retries, backup v2 archive integrity/finalization, v1 restore support, and staged rollback are unchanged. Backup command tests still cover busy locks, damaged archives, failure preserving an existing archive, and restore.
- The earlier polish already handled canceled/replaced imports, split-dialog dismissal guards, manual page validation, and clear backup completion messaging. This pass builds on those fixes. PDF Open and Finder/Explorer reveal scopes were reviewed but not changed; they still need installed-app checks.
- Gemini submits only the selected app-owned file, with existing bounded 429/server retries and explicit UI actions. No live request was made. The API key is excluded from archives and Rust status responses, but Settings still accepts it through a webview password field, as documented in `MAC_AUDIT_2026-09-12.md`; strict “never enters the webview” isolation remains unresolved. No credential, model setting, schema, or practice-test flow was changed here.

## Scope not measurable on this host

Installed startup, route navigation/paint, typing latency in a real WebView, SQL load-all time, import and backup wall time under autosave contention, Gemini network latency, process peak memory, actual long/image-heavy handbook throughput, and full installer size changes lack reproducible before/after measurements. The app currently refreshes all repositories after mutations, which may become a database bottleneck in large collections; changing that broad state contract without profiling would risk stale data. A 5,000-item Quick Find search is already under 3 ms in the local synthetic test. Record installed measurements before optimizing either path.
