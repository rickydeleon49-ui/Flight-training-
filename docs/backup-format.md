# Her Flight Deck portable backup format

_Status: documents the format as implemented in `src-tauri/src/backup.rs` on
`main` (release `0.5.1`). This is `format_version` **1**. It already exists
and ships today from the desktop app's Settings → Backup section — this
document is the versioned specification the code did not yet have written
down, plus the extension points the iOS work needs._

## File extension and container

- Extension: **`.hfdbackup`** (e.g. `Her Flight Deck — 2026-09-09.hfdbackup`).
  The iOS milestone should keep this extension rather than inventing a
  second one — a Mac-exported file must open on iOS and vice versa, and two
  extensions for one format would only create confusion about which builds
  can read which files.
- Container: a standard ZIP archive (via the `zip` crate, `Deflated`
  compression, `unix_permissions(0o600)` on every entry). Any ZIP-capable
  tool can list its contents; only Her Flight Deck understands what they mean.

## Internal structure (format_version 1)

```
manifest.json
her-flight-deck.db
her-flight-deck.db-wal      (present only if a checkpoint could not finish)
documents/
  <material-id>-<original-file-name>
  <material-id>-<original-file-name>
  ...
```

No `integrity.json` and no `files/pdf-parts/` subfolder exist as separate
concepts in format_version 1: split PDF parts are ordinary `study_materials`
rows with their own stored file, so they already live in `documents/` next
to everything else, and their relationship to the source material is a
column in the database (see below), not a manifest field. A future
format_version that adds a per-file manifest (see "Gaps" below) should keep
`documents/` as the single file tree and add the manifest as new JSON, not
reorganize the tree — every stored document's relative path is already the
value saved in `study_materials.file_path`, and changing that path scheme is
a breaking change independent of the archive format.

### `manifest.json`

```json
{
  "format": "her-flight-deck-complete-backup",
  "formatVersion": 1,
  "appVersion": "0.5.1",
  "createdAt": 1799999999
}
```

- `format` — a fixed string, checked exactly. Anything else is rejected
  before any other file in the archive is read.
- `formatVersion` — an integer. A restoring app must refuse a
  `formatVersion` it does not implement rather than guess. There is
  currently exactly one version, so the check is `== 1`; a future version 2
  must add a second accepted value with a code path for each, never silently
  reinterpret version 1 bytes under version 2 rules.
- `appVersion` — the exporting app's version string, shown to the user
  ("Backed up by version 0.5.1") so they can tell a backup is older than
  what they are running.
- `createdAt` — Unix seconds, shown as the backup date.

### `her-flight-deck.db` / `her-flight-deck.db-wal`

The live SQLite database, copied via `File::open` + `std::io::copy` (a plain
byte copy, not `VACUUM INTO` or the SQLite online backup API). Consistency
comes from the frontend, not the copy itself: before calling either backup
command, `AppRepository.checkpoint()` runs `PRAGMA wal_checkpoint(TRUNCATE)`
and **aborts the export with an error** if SQLite reports the checkpoint as
`busy` — a backup is never taken against a database with pending WAL writes
straddling the copy, it either checkpoints cleanly first or does not run.
The Rust-side WAL inclusion below is defense-in-depth for the narrow window
between that JS checkpoint succeeding and the Rust copy running, not the
primary consistency mechanism.

The write-ahead log file, when present, is included **only if it is
non-empty at copy time** — normally, after a successful `TRUNCATE`
checkpoint, it is zero bytes and is skipped entirely. SQLite folds a
non-empty WAL back into the main file automatically the next time it opens
the database, so carrying it is what keeps that narrow-window case lossless
rather than a source of corruption.

`her-flight-deck.db-shm` (the shared-memory index for the WAL) is
deliberately **never** included — it is regenerated by SQLite from the WAL
and is meaningless without the exact process that wrote it.

The tables carried inside the database (from `src-tauri/migrations/`):
courses/topics and study materials (`study_materials`, `tags`,
`material_tags`), AI-generated study guides and flashcards (`ai_study_sets`),
questions (`questions`), notes (`notes`), review/progress data embedded in
`study_materials` and `journal_entries`, schedule and prep items
(`schedule_events`, `event_materials`, `event_prep_items`), goals and
milestones (`goals`, `goal_checklist_items`, `milestones`), the flight
journal (`journal_entries`, `journal_materials`), finances (`transactions`,
`fund_goals`), the pilot toolkit (`pilot_toolkit`), and non-secret settings
(`settings`, `app_metadata`) — profile fields, accent color, and the
`last-complete-backup` record among them. **The Gemini API key is not a
column in any of these tables** — see "What is deliberately excluded" below.

### `documents/`

Every file under the app's private `documents/` directory, recursed and
added with its relative path prefixed by `documents/`. This is both the
original uploaded PDFs/images/text files **and** every generated PDF part
from automatic splitting (`split_pdf_automatically`) — a split part is not
distinguished from an original at the file-tree level, because it is not
distinguished from one at the database level either: it is its own
`study_materials` row with its own `file_path`, and that row is what the
restoring app uses to know it is "Part 2 of 3" of some other row.

Symlinks anywhere under `documents/` cause the whole export to fail rather
than being silently followed or silently skipped (`add_documents_to_archive`
rejects on `metadata.file_type().is_symlink()`) — nothing this app's own
import flow creates should ever be a symlink, so encountering one means the
data directory has been tampered with or corrupted, and guessing what to do
about it is worse than stopping.

## What is deliberately excluded

Never written to an archive, and structurally impossible to include by
accident because `allowed_archive_path` only recognizes `manifest.json`,
`her-flight-deck.db`, `her-flight-deck.db-wal`, and paths under
`documents/`:

- The Gemini API key (`gemini-key`, a plain file beside the database — see
  `src-tauri/src/secrets.rs` and `docs/ios/ARCHITECTURE.md` for why it is
  **not** in the OS keychain on desktop today).
- Any legacy OS-keychain entry from before the key moved to a plain file.
- `backups/` (the automatic pre-upgrade safety copies) and the restore
  staging directories (`.restore-staging`, `.restore-pending`) — a backup
  containing a backup, or a half-applied restore, would be nonsensical to
  restore from.
- Logs, caches, and anything outside the app's own data root — this format
  has no concept of "the rest of the filesystem" at all; `write_complete_backup`
  only ever reads from the two known paths above.
- Machine-specific absolute paths — every path recorded, both in the archive
  and in the database's `file_path` columns, is relative to the app's own
  data root, never an absolute OS path. That is what already makes a backup
  portable between two different user accounts on the same platform, and is
  exactly the property that also makes it portable between desktop and iOS:
  neither the archive nor the database says where "the app's data root" is
  on disk, so the restoring platform is free to put it wherever its sandbox
  requires.

## Integrity checking (format_version 1)

There is no per-file checksum list (no `integrity.json`) in format_version
1. Integrity is instead:

1. **At export** — a single atomic write. The archive is built at
   `<destination>.part`, and only `rename`d over the real destination once
   `ZipWriter::finish()` and `File::sync_all()` both succeed; a failure at
   any point removes the `.part` file, so a cancelled or crashed export
   never leaves a truncated file at the chosen name (`write_complete_backup`).
2. **At inspect / import** — the ZIP's own per-entry CRC-32 is not
   independently re-verified by this code (the `zip` crate can, but nothing
   here calls `entry.crc32()` against the decompressed bytes), but three
   independent checks stand in its place: (a) every extracted file's actual
   byte count must equal the size the ZIP central directory declared for it,
   or the restore is rejected; (b) `her-flight-deck.db`'s first 16 bytes
   must be the literal SQLite header (`SQLite format 3\0`), checked both
   before extraction (against the archive entry) and after (against the
   extracted file on disk, in case the disk write itself was corrupted);
   (c) a whole-archive size and entry-count ceiling
   (`MAX_RESTORE_FILES = 10_000`, `MAX_RESTORE_BYTES = 10 GiB`) is enforced
   incrementally while walking entries, so a hostile or corrupt archive
   cannot exhaust memory or disk before being rejected.

**Gap for a future format_version 2**: this does not detect single-byte
corruption inside a document that happens to match its declared size, and
it gives no per-file provenance for a Merge-mode restore that wants to
deduplicate by content hash across two libraries. A version 2 manifest
should add a `files` array of `{ path, sha256, bytes }` (SHA-256 chosen
over CRC-32 because Merge-mode deduplication needs a cryptographic-strength
hash to treat "same hash" as "same content" safely — see
`docs/ios/THREAT_MODEL.md`). This is additive: a v1 reader ignores an
unknown manifest field, and a v2 reader can still read a v1 archive by
falling back to the size-and-SQLite-header checks above when `files` is
absent. Do **not** make this change to `format_version` 1 in place — bump
to 2 and keep the version-1 reader working, per the format-version rule
above.

## Path-traversal and hostile-archive protection

Every entry, at both inspect time and stage time, goes through the same
gate before a single byte is written to disk:

- `entry.name()` is rejected outright if it contains a backslash (Windows
  separator smuggled into a ZIP written to look like a forward-slash path).
- `entry.enclosed_name()` — the `zip` crate's own traversal guard — must
  succeed; it refuses `..` components, absolute paths, and Windows drive
  prefixes before this code ever sees a `PathBuf`.
- The resulting path must satisfy `allowed_archive_path`: exactly
  `manifest.json`, `her-flight-deck.db`, `her-flight-deck.db-wal` (as
  non-directory entries), or anything under `documents/` (files or
  directories). Anything else — an unexpected top-level file, a path that
  isn't in the fixed set — is rejected by name, not silently skipped.
- Duplicate paths within one archive are rejected (`extracted_names`,
  a `HashSet<PathBuf>`) — two entries claiming the same destination is a
  crafted-archive technique for overwrite races, not something a real
  export produces.
- Any entry whose Unix mode bits mark it a symlink (`mode & 0o170000 ==
  0o120000`) is rejected outright, so an archive cannot plant a symlink that
  later points outside the documents directory once installed.
- `entry.by_index` / `by_name` bounds are the `zip` crate's own, and the
  10,000-entry / 10 GiB ceilings above are enforced incrementally, not only
  after a full read.

This is the same logic Milestone-1's threat model treats as already
answering "ZIP path traversal, hostile filenames, decompression bombs by
entry count, decompression bombs by expanded size" for format_version 1 —
see `docs/ios/THREAT_MODEL.md` for what is **not** yet covered (a
compression-ratio bomb: a small file whose *declared* size is itself huge
is still caught by the running byte total, but a single entry claiming a
plausible size while actually decompressing far past it relies on that same
running total catching it mid-copy, which it does via `std::io::copy`'s
return value check against `expected_size`).

## Restore semantics

Two restore kinds exist today, both **Replace**, distinguished by what they
replace (`RestoreKind` in `backup.rs`):

- **`Complete`** — from a portable `.hfdbackup`. Replaces the database
  *and* `documents/`.
- **`Database`** — from a local automatic safety copy (created before every
  version upgrade, kept as the 10 most recent). Replaces the database only;
  `documents/` is left untouched, because a safety copy never contained a
  copy of it in the first place.

Both follow the same staged, atomic, rollback-on-failure sequence, which is
the strategy `docs/ios/THREAT_MODEL.md` recommends reusing on iOS:

1. **Stage** (`stage_complete_restore` / `stage_local_restore`) — extract
   and fully validate into `.restore-staging/`, next to (never on top of)
   the live data. Nothing about the running app changes yet. A staging
   failure removes `.restore-staging/` and leaves current data untouched.
2. **Commit the plan** — on success, `.restore-staging/` is `rename`d to
   `.restore-pending/` with a small `restore.json` recording which kind of
   restore this is. A `rename` within the same filesystem is atomic on both
   platforms this ships on today.
3. **Apply on next launch** (`apply_pending_restore`, called from Tauri's
   `setup()` hook, before SQLite opens the database) — current
   `her-flight-deck.db*` (and `documents/`, for a `Complete` restore) are
   first `rename`d into a fresh `backups/<timestamp>-before-restore/`
   folder, *then* the pending files are `rename`d into place. If the
   protect step fails partway, everything already moved is moved back and
   the restore is abandoned with current data untouched. If the install
   step fails partway, partial installs are removed and the protected
   originals are restored — the app is never left with a database from one
   restore and documents from another, or a database that failed to write
   completely.
4. **Prune** — old automatic safety copies beyond the most recent 10 are
   removed only after a successful install.

**Desktop-specific step that iOS cannot reuse as-is**: `restart_for_restore`
calls `app.request_restart()` so step 3 runs before SQLite reopens on a
*fresh* process. iOS does not offer an equivalent app-initiated relaunch —
see `docs/ios/ARCHITECTURE.md` for the alternative (apply on next cold
launch, detected the same way `backup_if_upgraded` already detects "this is
the first run since an update").

### Merge is not implemented

There is no merge-mode restore today, on desktop or planned for the first
iOS milestone. Only Replace exists, and the Settings UI must not offer a
"Merge" choice until one is built and tested to the standard this document
and the threat model set for Replace. See `docs/ios/CHECKLIST.md` for the
tracked, deliberately-deferred plan.

## Size and count limits (format_version 1)

| Limit | Value | Enforced |
|---|---|---|
| Manifest size | 64 KiB | at inspect, before parsing |
| Archive entries | 10,000 | at inspect and at stage, incrementally |
| Total expanded bytes | 10 GiB | at inspect and at stage, incrementally |
| Automatic safety copies kept | 10 | after every successful restore |

iOS devices have materially less free storage headroom than a desktop, and
a 10 GiB ceiling is generous relative to a typical phone's available space
when the backup itself, the extraction staging copy, and the live data all
have to fit at once (roughly 3x the backup's size, transiently, during a
Replace restore). `docs/ios/ARCHITECTURE.md` recommends surfacing available
device storage before starting an iOS import rather than lowering this
ceiling — the limit exists to bound worst-case memory/entry-count handling,
not to predict what a given device can hold.
