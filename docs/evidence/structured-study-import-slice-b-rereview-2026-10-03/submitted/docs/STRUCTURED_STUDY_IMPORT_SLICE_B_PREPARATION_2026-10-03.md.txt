### 3.2 Deep dive: Decision D3 (Provenance without migration vs. waiting for M2) — corrected for BPREP-R2

Decision D3 represents an architectural tradeoff between immediate source adoption and formal database migration.

#### Observed source facts in current code
1. **Current Database Columns:** In `src-tauri/migrations/0007_ai_study.sql` and `0009_practice_tests.sql`, the columns `provider TEXT NOT NULL` and `model TEXT NOT NULL` exist in `ai_study_sets` and `practice_tests`. SQLite column types permit storing `'import'` and `''`.
2. **Current TypeScript Types:** In `src/domain/types.ts:245, 271`, `AiStudySet` and `PracticeTest` require `provider: "gemini"`.
3. **Current TypeScript Mappers:** In `src/data/repositories/documentRepository.ts:87, 97`, `mapAiStudySet` and `mapPracticeTest` hardcode `provider: "gemini"`, ignoring the stored column value.
4. **Current Writes:** `saveAiStudySet` and `savePracticeTest` in `documentRepository.ts:246, 278` hardcode `'gemini'` in their `INSERT` statements.

#### Inspection of Historical Tag `v0.5.1` (`2dbf6df3f66b18e087b5842fc554f8e733255a0e`)
Static inspection of the actual `v0.5.1` tag reveals:
1. **Migrations stop at 8:** `src-tauri/migrations/` in `v0.5.1` contains only `0001` through `0008_notes.sql`.
2. **Practice tests do not exist:** Migration `0009_practice_tests.sql` and `0010_debrief_operations.sql` are absent. The domain, repository, and UI have no concept of `practice_tests`.
3. **No newer-schema guard:** The backup restore implementation in `v0.5.1` (`backup.rs`) does not contain current main's `CURRENT_SCHEMA_VERSION` guard (added later during A1 restore retention work).
4. **Consequence:** Because `v0.5.1` has no practice tests and no schema version guard, restoring a modern schema-10 backup into `v0.5.1` is **unverified and unsupported**. It is incorrect to claim that practice tests remain functional or that restore succeeds cleanly without side effects on that historical version. Current `backup.rs` on `main` cannot retroactively protect older released binaries.

#### Comparison of Options for Owner Decision

| Option | What it does | Known Benefits | Disclosed Tradeoffs & Unknowns |
| --- | --- | --- | --- |
| **Option A (Proposed Default): Store `provider: "import"` without migration** | Widens TypeScript domain types to `provider: "gemini" \| "import"`. Mappers read through an allowlist. Native save writes `provider = 'import'`. Existing Gemini writes unchanged. | No migration files added (schema stays at version 10). Allows immediate offline study packet import without waiting for M2. | If an archive created with Slice B is restored into older binaries where mappers hardcode `"gemini"`, those older binaries display the imported set with Gemini labels. ### 3.3 Deep dive: Decision D2 (Create-new only vs. deferred replacement)

#### Proposed Flow: Create-New Only
- Every successful import produces a **new** `StudyMaterial` record with its own minted ID.
- The packet's guide (if present) is attached to the new material as an `ai_study_sets` row.
- The packet's test (if present) is attached to the new material as a `practice_tests` row.
- If the user imports the same packet file twice, two distinct materials are created. The preview modal informs the user: *"Will be imported as a new material."*

#### Why Replacement is Deferred
1. **Destructive Risk:** Today's schema has only one study set and one practice test per material. Replacing a study set completely overwrites existing flashcards and questions. If a user inadvertently targets an existing material, their prior notes and AI-generated study aids are permanently lost.
2. **Missing Versioning:** Version history and attempt tracking do not exist yet (scheduled for M2). Once M2 exists, replacement can create a new version while retaining the old version.
3. **Safety and Simplicity:** Create-new requires zero confirmation diffs, zero fingerprinting of existing rows, and cannot corrupt or delete prior data.

### 4.2 Hashing separation: Original-file hash vs. Canonical-content hash

A critical requirement of the contract (§3.5) is maintaining strict separation between two different hashes:

1. **Original-File SHA-256 (`originalFileSha256`):**
   - **Where computed:** In Rust (`src-tauri/src/study_packet.rs:107`), computed over the exact raw disk bytes read from the filesystem, including any UTF-8 BOM.
   - **Purpose:** Purely for display in the preview dialog and logs as a receipt for the user's reference (verifying which physical file was picked).
   - **Exclusion:** Never used for database deduplication, entity identity, or idempotency, because whitespace formatting, key ordering, and metadata comments would alter it without altering the study content.
2. **Canonical-Content SHA-256 (`contentHash`):**
   - **Where computed:** In TypeScript, computed by taking the SHA-256 of the UTF-8 bytes of `canonicalPersistenceJson(payload)`.
   - **Structure:** Defined in `src/logic/studyPacket/payload.ts:114-136`:
     ```json
     [
       "hfd-study-packet-content/1",
       ["Material Title"],
       ["import", "", "Title", "Summary", [["Heading", "Body"]], [["Front", "Back", null]], "Source Notes"],
       ["import", "", "Title", [["Question", ["Choice A", "Choice B"], 0, "Explanation", null]]]
     ]
     ```
   - **Properties:** Deterministic fixed-order JSON array. Completely excludes preview-only source claims, export IDs, choice IDs, item-level references, and file formatting. Changing an answer, card, heading, or source note changes this hash; changing key order or claims does not.
   - **Purpose:** Carried in `StructuredImportSaveOperation` as an operational digest.

### 4.3 Unified native IPC contract and defensive validation — corrected for BPREP-R3

To resolve the discrepancy between TypeScript and Rust DTOs and guarantee complete privacy-safe error handling:

#### 1. Unified Operation DTO
In TypeScript (`src/data/db.ts`):
```ts
export interface StructuredImportSaveOperation {
  operationId: string; // UUID v4 format; must match materialId
  materialId: string;  // UUID v4 format
  contentHash: string; // 64-char lowercase hex SHA-256
  material: { title: string };
  studySet: ImportedStudySetDraft | null;
  practiceTest: ImportedPracticeTestDraft | null;
}
```

In Rust (`src-tauri/src/study_packet.rs`):
```rust
#[derive(Debug, Clone, Deserialize)]
#[serde(rename_all = "camelCase", deny_unknown_fields)]
pub struct StructuredImportSaveOperation {
    pub operation_id: String,
    pub material_id: String,
    pub content_hash: String,
    pub material: ImportedMaterialDraft,
    pub study_set: Option<ImportedStudySetDraft>,
    pub practice_test: Option<ImportedPracticeTestDraft>,
}
```

#### 2. Unified Success and Failure Return Shapes
The command returns a typed result, never raw strings or arbitrary exceptions:
```rust
#[derive(Debug, Clone, PartialEq, Eq, Serialize)]
#[serde(tag = "status", rename_all = "snake_case")]
pub enum StructuredImportSaveResult {
    Saved { material_id: String },
    AlreadySaved { material_id: String },
}

#[derive(Debug, Clone, PartialEq, Eq, Serialize)]
#[serde(rename_all = "camelCase")]
pub struct NativeImportSaveFailure {
    pub code: &'static str,
    pub message: &'static str,
}
```

### 4.4 Idempotency vs. conflict: comparing actual stored content — corrected for BPREP-R3

The native transaction **never trusts the client-supplied `content_hash` as proof of equality**. Instead, equality is determined by inspecting the actual stored database rows:

1. When `material_id` exists in `study_materials`:
   - Query stored `study_materials.title`. If `stored.title != op.material.title`, refuse with `"conflict"` (title-only conflict).
   - If material was not created as a study guide import (`material_type != 'study_guide'`), refuse with `"conflict"`.
2. Inspect `ai_study_sets`:
   - If incoming has `studySet != null` and stored has no study set (or vice versa), refuse with `"conflict"` (presence change).
   - If both have study set: compare stored `summary`, parsed `sections_json`, parsed `flashcards_json`, `source_notes`, `provider`, `model`.
   - If stored `source_notes` differ, refuse with `"conflict"` (notes-only conflict).
   - If any section, card, or field differs, refuse with `"conflict"`.
3. Inspect `practice_tests`:
   - If incoming has `practiceTest != null` and stored has no test (or vice versa), refuse with `"conflict"` (presence change).
   - If both have test: compare parsed `questions_json` (questions, options, correctIndex, explanation), `provider`, `model`.
   - If any question or answer differs, refuse with `"conflict"`.
4. Result:
   - If all stored content matches the incoming operation payload: commit transaction and return `Ok(StructuredImportSaveResult::AlreadySaved { material_id })`.
   - If a client supplies a forged `content_hash` matching a prior save but changes the payload: the stored content comparison detects the difference and returns `"conflict"`.
   - If an unrelated material was created with the same ID: returns `"conflict"`.

### 4.5 Observable durability and recovery in WebAssembly (sql.js) — corrected for BPREP-R1

#### The Problem with Error Swallowing in `save(db)`
In `src/data/sqlJsDb.ts:31-41`, the existing `save(db)` function catches export and storage errors in a local `try/catch` and logs a warning with `console.warn`. A caller cannot observe failures from `save(db)` directly. Furthermore, after `COMMIT`, an SQL `ROLLBACK` cannot undo committed in-memory state, and replacing `const db` within closures fails without an indirection cell.

#### The Corrected Observable Persistence Architecture
1. **Observable Throwing Persistence Boundary:**
   Define `persistDurable(dbHandle): void`:
   ```ts
   function persistDurable(db: SqlJsDatabaseHandle): void {
     const bytes = db.export(); // throws if OOM
     let binary = "";
     for (let i = 0; i < bytes.length; i++) {
       binary += String.fromCharCode(bytes[i] as number);
     }
     localStorage.setItem(STORAGE_KEY, btoa(binary)); // throws QuotaExceededError
   }
   ```
2. **Handle Ownership via Mutable Indirection Cell:**
   The connection manager holds the active handle in a mutable cell:
   ```ts
   interface DatabaseCell {
     current: SqlJsDatabaseHandle;
   }
   ```
   All repository methods (`select`, `execute`, `persist`, `saveStructuredImportAtomically`) access `cell.current`.
3. **Serialized Access Through Save, Flush, and Recovery:**
   All write transactions are serialized via a FIFO lock queue (`saveMutex`). Unrelated writes cannot interleave between transaction start, commit, flush, and potential recovery.
4. **Pre-Operation Snapshot Capture:**
   Before executing `BEGIN IMMEDIATE`, the adapter captures an exact in-memory snapshot:
   ```ts
   const preOpSnapshot = cell.current.export();
   ```
5. **Execution Sequence & Recovery:**
   - `cell.current.run("BEGIN IMMEDIATE")`
   - Execute insert statements.
   - `cell.current.run("COMMIT")` (In-memory transaction completes).
   - Call `persistDurable(cell.current)`.
   - **If `persistDurable` throws (Export or Storage Failure):**
     * Catch error.
     * Close failed handle: `cell.current.close()`.
     * Instantiate clean handle: `cell.current = new SQL.Database(preOpSnapshot)`.
     * `localStorage` remains completely untouched (prior storage bytes preserved).
     * Throw typed `StorageDurabilityError("Study packet could not be saved to durable browser storage.")`.
6. **Retry Semantics after Durability Failure:**
   - Because `cell.current` was restored from `preOpSnapshot`, in-memory rows for `materialId` no longer exist.
   - A subsequent retry will NOT report `"already_saved"`; it cleanly re-executes the transaction.
   - Unrelated records committed *before* this operation are completely preserved.

### 4.6 Strict refusal when atomic adapter is unavailable

Her Flight Deck enforces zero data loss: **multi-row operations must be atomic.**
- If `db.saveStructuredImportAtomically` is undefined on the current `SqlDatabase` driver, `documentRepository.importStudyPacket(operation)` immediately throws `AtomicPersistenceUnsupportedError`.
- **Prohibition:** The repository must NEVER attempt sequential fallback calls (`create` followed by `saveAiStudySet` followed by `savePracticeTest`).

## 6. Scope boundaries and prohibitions

To prevent scope creep and protect the stability of Her Flight Deck, the following boundaries are strictly enforced for Slice B:

### In Scope for Slice B:
- Adding `save_structured_study_import` to `src-tauri/src/study_packet.rs` with pinned rusqlite connection, `BEGIN IMMEDIATE`, busy timeout, defensive revalidation, and stored-content idempotency.
- Adding `saveStructuredImportAtomically` to `SqlDatabase` in `src/data/db.ts` and implementing it in `src/data/tauriDb.ts` and `src/data/sqlJsDb.ts` (with observable throwing flush and snapshot recovery).
- Updating `src/domain/types.ts` to widen `provider` to `"gemini" | "import"`.
- Updating mappers and queries in `src/data/repositories/documentRepository.ts` to support `provider: "import"` with allowlist fallback.
- Refusing import with `AtomicPersistenceUnsupportedError` if the database adapter lacks atomic save support.
- Creating `ImportStudyPacketDialog.tsx` using `Dialog.tsx` with full A3 accessibility fallback.
- Adding "Import study packet…" entry point to `StudyLibrary.tsx`.
- Updating `MaterialDetail.tsx` to render imported-content titles, badges, and disclaimers when `provider === "import"`.
- Adding confirmation warning when regenerating Gemini content for a material that holds imported content.
- Unit and integration tests for all rows in §5.

### Strictly Out of Scope for Slice B:
- **No schema migrations:** No new SQL migration files in `src-tauri/migrations/`. Schema remains at version 10.
- **No replacement flow:** Replacing an existing material's guide or test is deferred (Decision D2).
- **No new production dependencies:** No `react-markdown`, `remark-gfm`, or other npm packages. (Markdown rendering is Slice C).
- **No external network calls:** Import is 100% offline. No telemetry, no Claude API, no Codex API, no Gemini calls during import.
- **No raw file retention:** Packet JSON is not copied into `documents/` (Decision D4).
- **No attempt tracking:** Question attempt history and durable item versions belong to M2.
- **No installer, signing, or release distribution:** Packaging, DMG creation, and signing remain governed by separate release runbooks.
