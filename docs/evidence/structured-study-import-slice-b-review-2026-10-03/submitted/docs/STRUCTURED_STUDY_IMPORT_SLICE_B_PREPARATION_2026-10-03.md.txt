### 3.2 Deep dive: Decision D3 (Provenance without migration vs. waiting for M2)

Decision D3 represents the single most significant architectural tradeoff in Slice B.

#### Context: How the database and mappers work today
1. **Database Schema:** In `src-tauri/migrations/0007_ai_study.sql` and `0009_practice_tests.sql`, the columns `provider TEXT NOT NULL` and `model TEXT NOT NULL` already exist in `ai_study_sets` and `practice_tests`. SQLite permits storing any text value, such as `'import'`, without schema changes.
2. **Current TypeScript Types:** In `src/domain/types.ts:245, 271`, `AiStudySet` and `PracticeTest` strictly require `provider: "gemini"`.
3. **Current TypeScript Mappers:** In `src/data/repositories/documentRepository.ts:87, 97`, the functions `mapAiStudySet` and `mapPracticeTest` ignore the column value and hardcode `provider: "gemini"`:
   ```ts
   // documentRepository.ts:87
   provider: "gemini",
   // documentRepository.ts:97
   provider: "gemini",
   ```
4. **Current Writes:** `saveAiStudySet` and `savePracticeTest` in `documentRepository.ts:246, 278` hardcode `'gemini'` in their `INSERT` statements.

#### The Proposed Default: Store `provider: "import"` without a migration
- **Implementation:**
  - Widen TypeScript domain types to `provider: "gemini" | "import"`.
  - Update mappers in `documentRepository.ts` to read the stored `provider` through an allowlist (`row.provider === "import" ? "import" : "gemini"`).
  - Slice B native command `save_structured_study_import` writes `provider = 'import'` and `model = ''`.
  - Existing Gemini save paths continue writing `'gemini'` unchanged.
- **The Tradeoff / Limitation:**
  - If a user imports a study packet in a build containing Slice B, creates a backup, and later restores that backup into an **older binary** (e.g., v0.5.1), the backup restore will succeed (because the schema version remains at 10, which older binaries accept).
  - However, because the older binary's mappers hardcode `provider: "gemini"`, the older binary will display the imported study guide with the title "Gemini study assistant" and the disclaimer "AI-generated study aid".
  - The underlying text, flashcards, questions, and answers remain 100% intact and functional. Only the attribution banner in older binaries is inaccurate.
  - When the database is opened again in the Slice B binary, it will correctly display "Imported study packet" and the imported-content disclaimer.

#### The Alternative: Wait for M2 Migration
- **Implementation:**
  - Block Slice B completely until M2.
  - Create `migrations/0011_study_material_versions.sql`, adding explicit content versions, stable item IDs, and distinct provenance tables.
  - Older binaries attempting to restore such a backup would cleanly reject it at the restore gate (`CURRENT_SCHEMA_VERSION < 11`), preventing the attribution mislabeling.
- **Tradeoff:**
  - Delays outside-assistant study import indefinitely until the full M2 milestone is designed, tested with real users, and implemented.
  - Users cannot import study packets into the current stable schema.

#### Recommendation for Owner Signoff
The proposed default is strongly recommended:
1. Backwards restore into older binaries is an edge case (users rarely downgrade after upgrading and creating new data).
2. Data integrity is fully preserved: no content is lost or corrupted.
3. It delivers immediate, high-value offline study packet capability without risking database migration bugs or delaying for M2.
**The owner must explicitly decide whether to accept this disclosed display quirk for older restored binaries or hold Slice B until M2.**

### 3.3 Deep dive: Decision D2 (Create-new only vs. deferred replacement)

#### Proposed Flow: Create-New Only
- Every successful import produces a **new** `StudyMaterial` record with its own minted ID.
- The packet's guide (if present) is attached to the new material as an `ai_study_sets` row.
- The packet's test (if present) is attached to the new material as a `practice_tests` row.
- If the user imports the same packet file twice, two distinct materials are created. The preview modal informs the user: *"Will be imported as a new material."*

#### Why Replacement is Deferred
1. **Destructive Risk:** Today's schema has only one study set and one practice test per material. Replacing a study set completely overwrites existing flashcards and questions. If a user inadvertently targets an existing material, their prior notes and AI-generated study aids are permanently lost.
2. **Missing Versioning:** Version history and attempt tracking do not exist yet (scheduled for M2). Once M2 exists, replacement can create a new version while retaining the old version.
3. **Safety and Simplicity:** Create-new requires zero confirmation diffs, zero fingerprinting of existing rows, and cannot corrupt or delete prior data.

### 4.2 Hashing separation: Original-file hash vs. Canonical-content hash

A critical requirement of the contract (§3.5) is maintaining strict separation between two different hashes:

1. **Original-File SHA-256 (`originalFileSha256`):**
   - **Where computed:** In Rust (`src-tauri/src/study_packet.rs:107`), computed over the exact raw disk bytes read from the filesystem, including any UTF-8 BOM.
   - **Purpose:** Purely for display in the preview dialog and logs as a receipt for the user's reference (verifying which physical file was picked).
   - **Exclusion:** Never used for database deduplication, entity identity, or idempotency, because whitespace formatting, key ordering, and metadata comments would alter it without altering the study content.
2. **Canonical-Content SHA-256 (`contentHash`):**
   - **Where computed:** In TypeScript, computed by taking the SHA-256 of the UTF-8 bytes of `canonicalPersistenceJson(payload)`.
   - **Structure:** Defined in `src/logic/studyPacket/payload.ts:114-136`:
     ```json
     [
       "hfd-study-packet-content/1",
       ["Material Title"],
       ["import", "", "Title", "Summary", [["Heading", "Body"]], [["Front", "Back", null]], "Source Notes"],
       ["import", "", "Title", [["Question", ["Choice A", "Choice B"], 0, "Explanation", null]]]
     ]
     ```
   - **Properties:** Deterministic fixed-order JSON array. Completely excludes preview-only source claims, export IDs, choice IDs, item-level references, and file formatting. Changing an answer, card, heading, or source note changes this hash; changing key order or claims does not.
   - **Purpose:** Carried in `StructuredImportSaveOperation` to verify idempotency on retry.

### 4.3 Operation identity, retry, and conflict semantics

To guarantee that network glitches, IPC timeouts, or UI retries never create duplicate database rows:

1. **Minting Operation Identity:**
   - When the user selects a file and validation succeeds, `ImportStudyPacketDialog` generates a single new `materialId` using `newId()` (UUID v4 format).
   - This `materialId` is bound to the preview state and remains fixed for the lifetime of that preview dialog.
2. **First Save Attempt:**
   - The dialog submits `StructuredImportSaveOperation`:
     ```ts
     interface StructuredImportSaveOperation {
       operationId: string; // Same as materialId
       materialId: string;
       contentHash: string; // SHA-256 of canonicalPersistenceJson(payload)
       material: { title: string };
       studySet: ImportedStudySetDraft | null;
       practiceTest: ImportedPracticeTestDraft | null;
     }
     ```
   - The native command checks if a material with `id = materialId` already exists:
     - If it does **not** exist: inserts rows inside an immediate transaction and returns `"saved"`.
3. **Idempotent Retry (Same ID, Same Content):**
   - If an IPC error occurs after the native commit, the user clicks "Try again" in the dialog.
   - The dialog resubmits the **same** `materialId` and `contentHash`.
   - The native command inspects the existing database row:
     - Material exists with `id = materialId`.
     - The stored study set and practice test match the incoming payload.
     - The native command returns `"already_saved"` without re-inserting or throwing.
     - The frontend treats `"already_saved"` as success and proceeds to refresh/navigate.
4. **Conflict Refusal (Same ID, Different Content):**
   - If `materialId` already exists but contains different content (or belonged to a prior material created elsewhere):
     - The native command immediately aborts and returns an error: `{ code: "conflict", message: "A material with this ID already exists with different content." }`.
     - The transaction is rolled back; nothing is overwritten.

### 4.4 Strict refusal when atomic adapter is unavailable

Her Flight Deck enforces a zero-data-loss architectural rule: **multi-row operations must be atomic.**

- In the desktop application, Tauri's SQL plugin uses a connection pool. Separate `db.execute("BEGIN")` and `db.execute("INSERT")` calls can execute on different pooled connections, making multi-statement client-side transactions non-atomic.
- Therefore, atomic saves require a dedicated native command (`save_structured_study_import`) executing on a single pinned rusqlite connection.
- In `documentRepository.ts:importStudyPacket(operation)`:
  ```ts
  if (!db.saveStructuredImportAtomically) {
    throw new AtomicPersistenceUnsupportedError(
      "Atomic persistence is not supported by the current database driver. Study packet import refused."
    );
  }
  ```
- **Prohibition:** Under NO circumstances may `documentRepository` fall back to executing sequential unpooled calls (`insertMaterial` followed by `saveAiStudySet` followed by `savePracticeTest`). A failure during sequential execution would leave an orphaned material without cards or tests.

### 4.5 Pinned native SQLite vs. sql.js durability and failure handling

| Dimension | Native Desktop (rusqlite / SQLite) | Browser / Dev Mode (sql.js / WebAssembly) |
| --- | --- | --- |
| **Connection model** | Single dedicated `Connection::open(&db_path)` pinned for the entire duration of the command. | Single in-memory WebAssembly database instance (`db: SqlJsDatabaseHandle`). |
| **Transaction start** | `connection.transaction_with_behavior(TransactionBehavior::Immediate)` with `busy_timeout(5s)` and `foreign_keys = ON`. | Direct SQL execution: `db.run("BEGIN IMMEDIATE")`. |
| **Contention & Locking** | If another thread or background process (e.g., backup snapshot) holds a write lock, rusqlite waits up to 5 seconds. If timeout expires, returns SQLite busy error. | In-memory; no external file contention. |
| **Commit boundary** | `tx.commit()` flushes database pages to disk (WAL mode). Once commit succeeds, data is durable across app crashes or power failure. | `db.run("COMMIT")` commits changes to the **in-memory** WebAssembly heap only. |
| **Durability boundary** | Disk write occurs during `tx.commit()`. | **Secondary flush required:** `save(db)` calls `db.export()` and serializes bytes to `localStorage` (or IndexedDB). |
| **Durability failure mode** | Disk full, I/O error during commit triggers rusqlite rollback. Uncommitted changes discarded. | **The A2-R6/R7 problem:** `COMMIT` succeeds in memory, but `localStorage.setItem()` throws (quota exceeded or serialization error). In-memory state now diverges from persisted storage! |
| **Durability failure handling** | Return typed error; database remains intact. | Must catch `save(db)` failure, roll back in-memory state or reload from previous snapshot, and report failure to user: *"Study packet could not be saved to browser storage."* |

## 6. Scope boundaries and prohibitions

To prevent scope creep and protect the stability of Her Flight Deck, the following boundaries are strictly enforced for Slice B:

### In Scope for Slice B:
- Adding `save_structured_study_import` to `src-tauri/src/study_packet.rs` with pinned rusqlite connection, `BEGIN IMMEDIATE`, busy timeout, and defensive revalidation.
- Adding `saveStructuredImportAtomically` to `SqlDatabase` in `src/data/db.ts` and implementing it in `src/data/tauriDb.ts` and `src/data/sqlJsDb.ts`.
- Updating `src/domain/types.ts` to widen `provider` to `"gemini" | "import"`.
- Updating mappers and queries in `src/data/repositories/documentRepository.ts` to support `provider: "import"` with allowlist fallback.
- Refusing import with `AtomicPersistenceUnsupportedError` if the database adapter lacks atomic save support.
- Creating `ImportStudyPacketDialog.tsx` using `Dialog.tsx` with full A3 accessibility fallback.
- Adding "Import study packet…" entry point to `StudyLibrary.tsx`.
- Updating `MaterialDetail.tsx` to render imported-content titles, badges, and disclaimers when `provider === "import"`.
- Adding confirmation warning when regenerating Gemini content for a material that holds imported content.
- Unit and integration tests for all rows in §5.

### Strictly Out of Scope for Slice B:
- **No schema migrations:** No new SQL migration files in `src-tauri/migrations/`. Schema remains at version 10.
- **No replacement flow:** Replacing an existing material's guide or test is deferred (Decision D2).
- **No new production dependencies:** No `react-markdown`, `remark-gfm`, or other npm packages. (Markdown rendering is Slice C).
- **No external network calls:** Import is 100% offline. No telemetry, no Claude API, no Codex API, no Gemini calls during import.
- **No raw file retention:** Packet JSON is not copied into `documents/` (Decision D4).
- **No attempt tracking:** Question attempt history and durable item versions belong to M2.
- **No installer, signing, or release distribution:** Packaging, DMG creation, and signing remain governed by separate release runbooks.
