## 1. Proposed User Outcome & Scope Boundaries

### Before and After Scenario
- **Current Main (Before):** Practice tests generated by Gemini or imported from packets live in `practice_tests` as an unversioned row with a raw JSON questions array. The existing test UI ([PracticeTestPanel.tsx](../src/pages/StudyLibrary/PracticeTestPanel.tsx)) stores progress purely in React component state. If a student answers 8 questions on a synthetic study packet, switches to the Flight Deck to check an event, closes the window, or quits the app, all 8 responses and their progress vanish. Retaking resets the in-memory counter; past attempts leave no record. Regenerating a test immediately overwrites the single row, destroying any active session. Forcing a choice between options forces guessing when the student honestly does not know the answer.
- **Proposed Increment (After):**
  - **Resume Anywhere:** Starting a practice test creates an atomic `in_progress` attempt bound to a stable content version. Navigating away, closing the window, or restarting the application preserves every confirmed response. Reopening the material displays an honest resume banner (*"In progress — 8 of 15 answered"*).
  - **Explicit "I Don't Know":** An explicit choice alongside multiple-choice options. It is tallied separately from incorrect guesses and unreached questions, encouraging honest assessment.
  - **Trustworthy Completion:** Submitting the final question executes an atomic completion transaction that computes an immutable result snapshot (`correct`, `incorrect`, `dont_know`, `unanswered`, `score_percent`).
  - **Educational Review:** The completed screen displays the score alongside a breakdown of missed and skipped questions with explanations and source references.
  - **Version Isolation:** Regenerating a test or importing a new material creates a new active version. Completed past attempts remain immutably anchored to the exact questions and options the student answered.
  - **Clean Retakes:** "Retake this test" leaves the completed attempt intact in history and opens a fresh attempt on the latest active version.

### Explicit Scope Boundaries
- **Included in this increment:** Single-material practice tests (both Gemini-generated and imported); resumable in-progress attempts across restarts; atomic per-question persistence; explicit "I don't know" distinction; immutable completed attempt snapshots; review of missed and "I don't know" items; retake action; content versioning upon test regeneration; additive database migration (Migration 11) with restart-safe legacy upgrade.
- **Explicitly deferred to later roadmap increments:** Multi-material / library-wide quiz sessions; flashcard review scheduling (FSRS / review queue, M2-3); source navigation page jumps (M4); AI feedback question extraction; official FAA exam certification claims; oral exam simulation; replacement import flows (overwriting existing materials).

## 3. Owner Decision Table (Preserving M2S-R1 Resolution)

The following decisions govern data retention, versioning, and product claims. Recommended defaults are presented with concrete alternatives:

| # | Decision | Recommended Default | Concrete Alternative | Rationale & Tradeoff |
|---|---|---|---|---|
| **D1** | **Source Deletion & Attempt Retention** | **Policy A (Retain Study Review for Completed Attempts):** Deleting a material deletes its PDF, active guide, and active test. Completed past attempts retain their frozen question text, options, explanations, student answers, and a `source_material_title` snapshot (`source_material_id = NULL`, `is_active = 0`). Inactive versions with zero completed attempts and all unfinished/draft attempts are pruned. An explicit "Erase study history" action in PR 2 removes past attempts/responses and unused historical versions; the current material/test and older backups remain. Minimal non-content retry tombstones prevent old requests from recreating erased history. | **Policy B (Strict Summary Only):** Delete all questions, options, and responses on material deletion. Storing retained text takes space proportional to test size. Policy B saves space but permanently destroys the ability to review missed questions. Policy C treats tests as disposable. |
| **D2** | **Regeneration vs. In-Progress Session** | **Abandon with notice:** Regenerating a practice test creates a new active version. Any *in-progress* attempt on the prior version is transitioned to `abandoned` with notice: *"Practice test was regenerated; unfinished attempt closed."* Completed attempts remain intact on their version. | **Disallow regeneration while test in progress:** Prevent the user from regenerating until the current attempt is either finished or explicitly cancelled. | Abandoning avoids scoring responses against replaced question keys while letting the user regenerate when desired. Completed history remains unaltered. |
| **D3** | **Session Scope** | **Single-material only:** Practice tests are strictly scoped to one selected study material in this increment. | **Multi-material quiz pools:** Allow cross-material custom test generation immediately. | Single-material delivers immediate daily utility without introducing complex cross-material schemas or query bottlenecks. |
| **D4** | **Legacy Corrupt `questions_json`** | **Safe skip with durable status:** If an existing `practice_tests` row contains malformed JSON or zero valid questions, record the sanitized `legacy_error = 'MALFORMED_QUESTION'`, skip version creation, leave the row intact, and display an honest UI notice: *"Existing test could not be migrated; please regenerate."* | **Fail migration:** Abort database upgrade on malformed historical JSON. | The application must start safely even if an older Gemini call stored malformed JSON. The migration never aborts or drops unmigrated data silently. |
| **D5** | **Practice Score Wording** | **Informational practice label:** Display *"Practice result from your material ({n}%). Not an official FAA knowledge test score or certification of flight readiness."* | **Generic score display:** Show only "{n}% correct" without regulatory context. | Meets product truthfulness standards (ROADMAP §2) and prevents false confidence regarding FAA knowledge exam readiness. |

## 5. Backup, Restore & Downgrade Specification (Addressing M2S-R3)

- **Database Format Version:** Migration 11 increments `CURRENT_SCHEMA_VERSION` in [lib.rs](../src-tauri/src/lib.rs) from 10 to 11.
- **Backup Creation:** Existing backup engine ([backup.rs](../src-tauri/src/backup.rs)) captures the SQLite database file and document directory into a ZIP archive. The new tables are inside the primary database and are backed up automatically.
- **Schema-Aware Restore Validation (backup.rs):**
  - **Schema <= 10 (Supported Old Archives):** `verify_application_database` runs read-only on staging. Validates SQLite format, quick_check, and baseline tables (`settings`, `study_materials`). New tables are **not** required. Staged plan installs cleanly; on application startup, missing migrations (including 11) and legacy conversion run in order.
  - **Schema 11 (Current Archives):** Requires presence of all 5 new tables (`practice_test_versions`, `practice_test_items`, `practice_attempts`, `practice_responses`, `practice_session_operations`). Validates semantic invariants:
    1. Foreign keys on with zero violations (`PRAGMA foreign_key_check` empty).
    2. Version ownership: every response's item belongs to the attempt's version.
    3. Active uniqueness: at most one active version and at most one in-progress attempt per material.
    4. Result consistency: recompute counts and rounded score from frozen items/responses, compare all stored tallies, and verify state/time/choice bounds and receipt shapes. Non-null fields alone do not establish consistency. Check required columns/indices/triggers as well as tables (Appendix E).
  - **Schema > 11 (Newer Archives):** Refused immediately with the standard error: *"That backup was created by a newer database format. Update the app first."*
- **Downgrade Boundary:** The inspected schema-10 source rejects newer-format backups through its archive validator. No guarantee is made for every historical binary. Raw database downgrade or use of an upgraded database with an old app is unsupported; app version and database schema version are distinct.

# Technical Appendices

## Appendix A: Additive Schema & SQL Invariants (Addressing M2S-R1 & M2S-R2)

```sql
-- Migration 0011_practice_sessions.sql
-- Additive tables for durable, versioned, resumable practice tests.

-- 1. Versioned practice tests (anchors items and historical attempts)
CREATE TABLE IF NOT EXISTS practice_test_versions (
    id                    TEXT PRIMARY KEY,
    source_material_id    TEXT REFERENCES study_materials(id) ON DELETE SET NULL,
    history_key           TEXT NOT NULL, -- Original material identity, retained after deletion
    source_material_title TEXT NOT NULL,
    version_number        INTEGER NOT NULL DEFAULT 1,
    provider              TEXT NOT NULL DEFAULT 'gemini',
    model                 TEXT NOT NULL DEFAULT '',
    title                 TEXT NOT NULL DEFAULT '',
    content_hash          TEXT NOT NULL,
    created_at            TEXT NOT NULL,
    is_active             INTEGER NOT NULL DEFAULT 1 CHECK (is_active IN (0, 1))
);

-- At most one active version per study material
CREATE UNIQUE INDEX IF NOT EXISTS uq_active_practice_version
    ON practice_test_versions(source_material_id)
    WHERE is_active = 1 AND source_material_id IS NOT NULL;

-- 2. Stable practice questions belonging to a test version
CREATE TABLE IF NOT EXISTS practice_test_items (
    id            TEXT PRIMARY KEY,
    version_id    TEXT NOT NULL REFERENCES practice_test_versions(id) ON DELETE CASCADE,
    ordinal       INTEGER NOT NULL,
    question_text TEXT NOT NULL,
    options_json  TEXT NOT NULL,
    correct_index INTEGER NOT NULL,
    explanation   TEXT NOT NULL DEFAULT '',
    source_page   INTEGER,
    UNIQUE(version_id, ordinal)
);

CREATE INDEX IF NOT EXISTS idx_practice_items_version
    ON practice_test_items(version_id, ordinal);

-- 3. Individual user attempts on a specific test version
CREATE TABLE IF NOT EXISTS practice_attempts (
    id                    TEXT PRIMARY KEY,
    version_id            TEXT NOT NULL REFERENCES practice_test_versions(id) ON DELETE RESTRICT,
    source_material_id    TEXT REFERENCES study_materials(id) ON DELETE SET NULL,
    source_material_title TEXT NOT NULL,
    started_at            TEXT NOT NULL,
    completed_at          TEXT,
    status                TEXT NOT NULL CHECK (status IN ('in_progress', 'completed', 'abandoned')),
    revision              INTEGER NOT NULL DEFAULT 0 CHECK (revision >= 0),
    total_questions       INTEGER NOT NULL,
    answered_count        INTEGER NOT NULL DEFAULT 0,
    correct_count         INTEGER NOT NULL DEFAULT 0,
    incorrect_count       INTEGER NOT NULL DEFAULT 0,
    dont_know_count       INTEGER NOT NULL DEFAULT 0,
    score_percent         REAL
);

-- At most one in-progress attempt per study material
CREATE UNIQUE INDEX IF NOT EXISTS uq_single_in_progress_attempt
    ON practice_attempts(source_material_id)
    WHERE status = 'in_progress' AND source_material_id IS NOT NULL;

CREATE INDEX IF NOT EXISTS idx_practice_attempts_material
    ON practice_attempts(source_material_id, status);

-- 4. Recorded responses per item within an attempt
CREATE TABLE IF NOT EXISTS practice_responses (
    id             TEXT PRIMARY KEY,
    attempt_id     TEXT NOT NULL REFERENCES practice_attempts(id) ON DELETE CASCADE,
    item_id        TEXT NOT NULL REFERENCES practice_test_items(id) ON DELETE CASCADE,
    selected_index INTEGER,
    is_dont_know   INTEGER NOT NULL DEFAULT 0 CHECK (is_dont_know IN (0, 1)),
    is_correct     INTEGER NOT NULL DEFAULT 0 CHECK (is_correct IN (0, 1)),
    answered_at    TEXT NOT NULL,
    UNIQUE(attempt_id, item_id),
    CHECK (
        (is_dont_know = 1 AND selected_index IS NULL) OR
        (is_dont_know = 0 AND selected_index IS NOT NULL AND selected_index >= 0)
    )
);

CREATE INDEX IF NOT EXISTS idx_practice_responses_attempt
    ON practice_responses(attempt_id);

-- 5. Persistent operation receipts for idempotent replay
CREATE TABLE IF NOT EXISTS practice_session_operations (
    operation_id   TEXT PRIMARY KEY,
    action         TEXT NOT NULL,
    request_hash   TEXT NOT NULL,
    applied_at     TEXT NOT NULL,
    result_json    TEXT NOT NULL,
    history_key    TEXT NOT NULL,
    attempt_id     TEXT NOT NULL, -- No FK: erased attempts leave non-content tombstones
    is_erased      INTEGER NOT NULL DEFAULT 0 CHECK (is_erased IN (0, 1))
);

-- 6. Triggers enforcing that an item belongs to the attempt's version on INSERT or UPDATE
CREATE TRIGGER IF NOT EXISTS trg_enforce_response_item_version_insert
BEFORE INSERT ON practice_responses
FOR EACH ROW
BEGIN
    SELECT RAISE(ABORT, 'Item does not belong to attempt version')
    WHERE (
        SELECT version_id FROM practice_attempts WHERE id = NEW.attempt_id
    ) != (
        SELECT version_id FROM practice_test_items WHERE id = NEW.item_id
    );
END;

CREATE TRIGGER IF NOT EXISTS trg_enforce_response_item_version_update
BEFORE UPDATE OF item_id, attempt_id ON practice_responses
FOR EACH ROW
BEGIN
    SELECT RAISE(ABORT, 'Item does not belong to attempt version')
    WHERE (
        SELECT version_id FROM practice_attempts WHERE id = NEW.attempt_id
    ) != (
        SELECT version_id FROM practice_test_items WHERE id = NEW.item_id
    );
END;

-- 7. Trigger handling material deletion cleanup (Policy A)
CREATE TRIGGER IF NOT EXISTS trg_cleanup_material_delete
AFTER DELETE ON study_materials
FOR EACH ROW
BEGIN
    UPDATE practice_session_operations
    SET is_erased = 1, result_json = 'null'
    WHERE attempt_id IN (SELECT id FROM practice_attempts
        WHERE source_material_id IS NULL AND status IN ('in_progress', 'abandoned'));

    DELETE FROM practice_attempts
    WHERE source_material_id IS NULL AND status IN ('in_progress', 'abandoned');

    UPDATE practice_test_versions
    SET is_active = 0
    WHERE source_material_id IS NULL AND is_active = 1;

    DELETE FROM practice_test_versions
    WHERE source_material_id IS NULL
      AND id NOT IN (SELECT DISTINCT version_id FROM practice_attempts WHERE status = 'completed');
END;

-- 8. Durable migration tracking for legacy practice_tests
ALTER TABLE practice_tests ADD COLUMN legacy_migrated_at TEXT;
ALTER TABLE practice_tests ADD COLUMN legacy_error TEXT;
```

## Appendix B: Normative Persistence Contracts & Wire Shapes (Addressing M2S-R2)

### 1. Durable Operation Identity & Replay Semantics
- **Persistent Storage:** Every state-modifying action requires an `operationId` (UUID v4). Operations commit atomically with an entry in `practice_session_operations`:
  - `operation_id`: Primary key.
  - `action`: String name of the executed operation.
  - `request_hash`: SHA-256 of the canonical JSON request payload (sorted keys, compact whitespace).
  - `applied_at`: Authoritative UTC ISO timestamp of execution.
  - `result_json`: Stored JSON result returned to the client.
- **Transaction Replay Sequence:**
  1. Validate incoming request structure and payload bounds.
  2. Open transaction (`BEGIN IMMEDIATE` in rusqlite / connection owner mutex in browser).
  3. Inspect `practice_session_operations WHERE operation_id = ?`:
     - **Exact Match:** If found and `sha256(request) == request_hash`, immediately return `result_json` without re-evaluating state changes. (e.g. if retake was acknowledged as lost, replay returns the already-created attempt without abandoning it or creating another).
     - **Conflict:** If found but `sha256(request) != request_hash`, abort transaction with `OPERATION_CONFLICT`.
  4. If unseen, execute state mutation, write row to `practice_session_operations`, and `COMMIT`.
- **Receipt Lifecycle:** Receipts are associated by `history_key` and `attempt_id`, included in backup/restore, and remain while their study history remains. Deletion/erasure converts receipts for removed attempts to non-content tombstones (`is_erased = 1`, `result_json = "null"`); matching old retries return `INVALID_STATE`, not a new mutation. No choices/results remain in tombstones. See Appendix E for precedence and erasure behavior.

### 3. Payload Validation, Authoritative Clock & Ownership Rules
- **Strict Payload Checking:** Any unknown JSON keys at the root or within nested objects result in immediate rejection with `INVALID_ARGUMENT`. Request payloads cannot exceed 64 KiB.
- **Boundaries:** String lengths (questions <= 10,000 code points, options 2–8 items of <= 1,000 code points, explanations <= 5,000 code points). `selectedIndex` must satisfy `0 <= selectedIndex < options.length`.
- **Authoritative Clock:** Production timestamps (`started_at`, `completed_at`, `answered_at`, `applied_at`) are generated by the server/native backend using UTC `nowIso()`. Tests inject an explicit clock interface. These request shapes accept no client timestamps; an extra timestamp field is rejected as an unknown key. No remote server is introduced.
- **Strict Ownership:**
  - `start_or_resume` and `retake_attempt` verify that `versionId` belongs to `materialId` and is currently active (`is_active = 1`).
  - `record_response` verifies that `attempt.status == 'in_progress'`, and that `item.version_id == attempt.version_id`.
  - Updating responses: A student may change their selection while `in_progress`. Re-selecting the same option is a no-op; changing an answer updates `selected_index`, `is_dont_know`, `is_correct`, and `answered_at`.

### 4. Scoring Derivation, Cursor & Navigation
- **Scoring Authority:** Computed entirely on the backend during `complete_attempt` by joining `practice_responses` with frozen `practice_test_items`. Client scores or correctness flags are disregarded.
- **Tally Calculations:**
  - `correct_count`: count of responses where `is_correct = 1`.
  - `dont_know_count`: count of responses where `is_dont_know = 1`.
  - `incorrect_count`: count of responses where `is_dont_know = 0 AND is_correct = 0`.
  - `unanswered_count`: `total_questions - answered_count`.
  - `score_percent`: `round((correct_count / total_questions) * 100.0, 1)`.
- **Early Completion:** The student may submit a test before answering all questions. Unanswered questions are not recorded as responses and are tallied as `unanswered_count` with 0 points.
- **Resume Cursor:** `nextUnansweredOrdinal` is calculated as the lowest `ordinal` in `practice_test_items` without a corresponding entry in `practice_responses`.

### 5. Failure, Durability & Recovery Sequence
- **Native rusqlite:** Uses dedicated connection with `busy_timeout(5 s)`, `foreign_keys = ON`, and `BEGIN IMMEDIATE`. Any lock timeout or disk error triggers automatic transaction rollback.
- **Browser sql.js:** Operations run through `connectionOwner.ts` mutex lock. The operation performs in-memory transaction, commits the transaction, then exports/encodes/stores the database through the existing `localStorage` durable-write path, and releases mutex. If durable write fails, it reverts the in-memory database to the last verified export. If recovery fails, it marks the database disabled (`DatabaseDisabledError`) to prevent corrupt writes.
- **Unconfirmed Save Handling:** UI maintains a transient pending indicator until IPC confirms. If the app exits or crashes before acknowledgment, the database either committed atomically or rolled back cleanly; upon restart, the UI refreshes current state through repository reads. During a running session it retries the original pending action/payload/operation ID unchanged; a receipt replay may be historical, so it then reads current state before editing. It never substitutes start/resume for an unknown-commit retake or completion.

## Appendix C: Migration, Legacy Conversion & Writer Integration Plan (Addressing M2S-R3)

### 1. Initialization Entry Points & Conversion Sequence
- **Desktop:** SQL migrations registered in [lib.rs](../src-tauri/src/lib.rs) execute during `Database.load` in [createTauriDatabase](../src/data/tauriDb.ts). Await native conversion after load, before resolving database/repository readiness. Session/test writers also enforce conversion readiness; unrelated IPC handlers are not globally stopped.
- **Browser (development only):** Conversion runs after `applyMigrations` in [createSqlJsDatabase](../src/data/sqlJsDb.ts), before returning the adapter, using the owned transaction/export/store path. Storage failure restores the last stored bytes and prevents exposing a falsely ready session repository.
- **Conversion Transaction:**
  - Selects legacy rows: `SELECT * FROM practice_tests WHERE legacy_migrated_at IS NULL AND legacy_error IS NULL AND NOT EXISTS (SELECT 1 FROM practice_test_versions WHERE source_material_id = practice_tests.source_material_id)`.
  - Validates question structure: checks that `questions_json` is valid JSON, contains 1–200 questions, and each question has valid text, options (2–8), and `correctIndex`.
  - If valid: generates version/item UUID v4 identities once inside the transaction and persists them with the conversion marker; restart uses the persisted identities, and a collision fails/rolls back rather than overwriting another record, inserts version 1 (`is_active = 1`), inserts items, and sets `legacy_migrated_at = nowIso()`.
  - If corrupt: sets `legacy_error = 'MALFORMED_QUESTION'`; leaves row intact without crashing startup.

### 2. Writer Hooks and Atomic Ordering
- **Gemini Save ([documentRepository.ts](../src/data/repositories/documentRepository.ts)):**
  1. Deactivate existing active version: `UPDATE practice_test_versions SET is_active = 0 WHERE source_material_id = ? AND is_active = 1;`
  2. Abandon in-progress attempt under D2: `UPDATE practice_attempts SET status = 'abandoned', completed_at = ? WHERE source_material_id = ? AND status = 'in_progress';`
  3. Insert new active version: `INSERT INTO practice_test_versions (..., is_active = 1);`
  4. Insert items: `INSERT INTO practice_test_items (...);`
  5. Update legacy row and marker: `INSERT INTO practice_tests (..., legacy_migrated_at, legacy_error) VALUES (..., ?, NULL) ON CONFLICT(source_material_id) DO UPDATE SET ..., legacy_migrated_at = ?, legacy_error = NULL;`
  All 5 steps execute inside a single atomic transaction.
- **Slice B Import ([src-tauri/src/study_packet.rs](../src-tauri/src/study_packet.rs)):**
  The native command and [browser/test structuredImportTransaction](../src/data/structuredImportTransaction.ts) create a new material, insert `practice_tests` with `legacy_migrated_at = nowIso()`, inserts version 1 into `practice_test_versions`, and inserts items in its existing `save_structured_study_material_atomically` transaction.
- **Material Deletion ([documents.ts](../src/services/documents.ts)):**
  Calls `removeMaterialWithFile`: stages PDF deletion, executes `DELETE FROM study_materials WHERE id = ?`. Triggers enforce Policy A: draft attempts deleted, versions deactivated, versions with 0 completed attempts pruned, completed attempts preserved. Staged PDF deletion is finalized only after database commit, retaining existing rollback behavior. `removePracticeTest` additionally deactivates that material's active version and removes unfinished attempts/unused historical versions in one owned transaction; completed review remains. It does not delete the PDF. Repository `remove` applies Policy A when deleting the whole material.
- **PR 1 / PR 2 Compatibility:** In PR 1, `documentRepository.listPracticeTests` continues reading active test data normally. The old UI continues to work against the legacy table while new version tables are maintained concurrently.

### 3. Schema-Aware Backup & Restore Validation
`backup.rs::verify_application_database` reads the staged database without mutating it.
- **Schema <= 10:** Checks baseline tables (`settings`, `study_materials`) and `PRAGMA quick_check`. New tables are not required.
- **Schema 11:** Checks all 5 new tables. Executes query verifying zero orphan items (`NOT EXISTS (SELECT 1 FROM practice_test_items i LEFT JOIN practice_test_versions v ON i.version_id = v.id WHERE v.id IS NULL)`), zero cross-version responses, at most one active version per material, and consistent completed scores.
- **Schema > 11:** Rejected immediately with *"That backup was created by a newer database format. Update the app first."*

## Appendix E: Reviewer-set Engineering Decisions and Source Acceptance Criteria

These bounded amendments complete the planning contract. They are future implementation requirements, not evidence that production commands or restore tests already exist. If an appendix sketch conflicts, these rules govern. The owner approves product scope; routine storage/transaction choices are settled here.

### Operation ordering, responses and reads

- All five action request examples in Appendix B show required keys; reject unknown keys, wrong JSON types, missing fields and oversized requests. `operationId` is UUID v4. Referenced IDs are nonempty ASCII `[A-Za-z0-9_.-]` strings of at most 128 characters, consistent with existing material IDs. `expectedRevision` is a nonnegative safe integer bounded at 2,147,483,647; reject overflow before mutation. `selectedIndex` is NULL only for `isDontKnow = true`; otherwise a safe integer in the frozen option range. Each response correctness value is recomputed from the frozen key.
- Fixed sanitized codes/messages cover `INVALID_ARGUMENT`, `INVALID_STATE`, `NOT_FOUND`, `OPERATION_CONFLICT` and `STORAGE_ERROR`; adapters also retain existing unsupported-atomic-driver and disabled/durability refusals. Do not expose payloads, file paths or raw SQL errors. Native and browser validators use the same required field/type/bound rules.
- Inside one owned transaction: validate request, look up receipt by operation ID, compare canonical request hash and action, reject changed-input reuse, reject a matching erased tombstone, or return the original stored result. Always end the read/replay transaction before returning. Only an unseen operation checks current state and changes it. Canonicalize the strictly typed request with sorted keys/compact JSON identically in native/browser; derive the hash locally, never trust a client digest.
- `start_or_resume` requires the requested current active version and returns the single existing in-progress attempt or creates revision 0. Two concurrent starts serialize and return the same applicable attempt. `retake_attempt` also requires the current active version and `expectedAttemptId` matching the current in-progress attempt, or NULL if none exists. It atomically abandons that attempt and creates a fresh one; two different retakes from the same stale expectation cannot abandon each other's new attempt. A receipt replay returns its original created attempt even if later activity changed current state; refresh before using it.
- `record_response`, `complete_attempt` and `abandon_attempt` require an existing in-progress attempt and a matching `expectedRevision` after the receipt lookup. Mismatch returns `INVALID_STATE` without writes; the UI refreshes and requires a new intended action rather than automatically overwriting a newer answer. Changed response/completion/abandon increments revision; an identical already-stored choice is a no-op with the same answered time/revision but still records its new operation receipt. Regeneration's automatic abandonment also increments revision. Closed attempts reject new mutations; identical committed retries replay only, including late response retries.
- `answered_count` is the count of response rows, and counts/score are derived from frozen items rather than client fields or trusted stored flags. Exactly one of correct/incorrect/dont-know accounts for each response, unanswered is total minus answered, and all totals are nonnegative and sum consistently. Divide by the nonzero frozen item count, then round percent to one decimal. Completion snapshots/timestamps never change after commit. An all-answered in-progress attempt has `nextUnansweredOrdinal = null`; completion remains explicit. Navigation can revisit answered items and skip unanswered ones; immediate training feedback is the recommended UI default.
- The repository exposes current-attempt refresh by ID/material and completed-history reads by stable `history_key`; replayed snapshots do not substitute for these reads. Keep a single pending action in UI memory, with its original operation ID/payload for retry. Across app restart, query persisted current state; do not claim an unsaved UI operation ID survives. Refresh failure after a commit is a read failure, not permission to execute a fresh retake. An unsupported atomic driver refuses before the first write. Native lock wait stays bounded to five seconds and transaction errors roll back; sql.js retains its current localStorage durability/recovery and FK reinitialization behavior, including refusal after failed recovery. No IndexedDB/OPFS migration is authorized.

### Conversion, history and restore

- Existing imported packets may contain 200 questions; the session/conversion ceiling is 200, with no silent truncation. Preserve the existing PracticeQuestion representation: bounded nonempty question text (at most 10,000 code points), 2–8 nonempty options (at most 1,000 each), in-range integer `correctIndex`, explanation at most 5,000, and `sourcePage` NULL or integer 1–1,000. Keep accepted import validation's tighter limits and payload semantics unchanged; imported sourcePage remains NULL. Validate an entire legacy test before inserting any of its items. Malformed, empty or out-of-bound historical content is retained with `MALFORMED_QUESTION` and unavailable to new sessions; do not silently drop invalid questions.
- Conversion and new writers set `history_key` to the original material ID and persist markers/version/items atomically. Existing versions with an unset marker require bounded reconciliation against the legacy content; mark a matching version migrated, but refuse a conflicting state rather than silently using stale content. Content hash/version number derives from normalized persisted content; replacement validates all new content before deactivation. Storage/interruption failure rolls back the conversion/writer transaction, preserving legacy content and prior usable version/progress. SQL DDL may already have committed; retry conversion on the next successful initialization rather than pretending to roll back a previously applied migration.
- PR 1 keeps the existing legacy read shape and old UI working. Repository status also exposes sanitized conversion failure; PR 2 renders the regeneration notice. No PR 1 UI claim is made. Data writes remain behind the readiness promise/owned command path for both drivers.
- Completed detached reviews are grouped by retained `history_key`, not by a now-NULL material FK or a nonunique title. Source deletion prunes unfinished data and tombstones their receipts; completed receipts remain with retained review. PR 2's explicit erase-history transaction cancels/removes all historical attempts/responses for the selected history key, removes unused inactive versions, and replaces associated receipt results with non-content tombstones. Current material/legacy test/active version can remain for future new practice; erasure does not remove PDFs or prior backups. Erased receipts keep only operation identity/hash/action/time/history association sufficient to refuse replay, with no saved choice/result content. Disclose that boundary in the UI rather than promising deletion of every copy.
- Schema-aware read-only archive validation retains migration-history/ceiling and existing file/staging checks. Supported schema <= 10 does not require new tables; schema 11 requires all new columns, uniqueness indices and ownership triggers plus receipt structures; later schemas refuse. Validate every item/attempt/response owner, choice bounds/correctness, active/in-progress uniqueness, detached inactive state, frozen item count, allowed status and timestamps. Recompute completed counts/rounded score and compare every stored total, not just non-null score/time. Validate receipt key/hash/action/result shape and history association; erased tombstones may refer to removed attempts, and historical replay results may differ from current mutable state.
- Restore startup applies missing DDL, then conversion, then semantic validation before exposing sessions. Preserve existing pre-upgrade copies and staged-restore recovery; never mutate an archive in the read-only verifier or delete recovery files merely because conversion failed. A conversion I/O failure returns a sanitized failure and prevents session writes until safe retry. Verify staged and startup rollback behavior in disposable fixtures before claiming source acceptance.
